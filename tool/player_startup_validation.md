# Windows player startup validation

Use Flutter 3.47.6 and the verified Windows core SDK. The normal Flutter
renderer remains enabled, including Impeller. Windows warms one hidden player
engine after the logged-in main window renders and after a player exits. It
does not attach credentials, open a decoder, or request media while idle.
Playback adopts that engine; closing/logging out retires it. A failed prewarm
falls back to a normal process launch. Other desktop platforms retain cold
launches and share the concurrent metadata preparation.

Build the ordinary `lib/main.dart` release target before benchmarking:

```powershell
$env:RILLIGHT_CORE_PREFIX_WINDOWS_X64 = "$PWD/build/local-current-windows-sdk"
flutter build windows --release
python tool/player_startup_bench.py --executable build/windows/x64/runner/Release/rillight.exe --out build/player-validation/startup-cold --runs 3
python tool/player_startup_bench.py --executable build/windows/x64/runner/Release/rillight.exe --prepared --warm --out build/player-validation/startup-warm --runs 3
python tool/player_startup_bench.py --executable build/windows/x64/runner/Release/rillight.exe --prepared --warm --metadata-delay-ms 1000 --out build/player-validation/startup-delayed --runs 3
```

Output directories must be new. The fixture media must already exist under
`build/player-validation/media` (generated by `tool/player_smoke.ps1`). Requires
an interactive Windows desktop and Pillow. The harness uses synthetic
credentials, isolated settings/cache and a loopback Emby fixture. It captures
the real window's central test-pattern panels and checks changing pixels.
It rejects ordinary desktop/poster colors as first-frame evidence.

`visibleMs` measures an HWND becoming visible. `coloredFrameMs` measures the
first screen sample matching the synthetic video. `changingFrameMs` confirms
later pixel changes; sampling intervals mean this is not frame-accurate
instrumentation. Warm measurements start at the play/start signal, after the
hidden engine is ready; `prewarmMs` separately records background startup.
`--prepared` reproduces the production host's concurrent metadata handoff.
The benchmark does not drive the detail-page tap, measure physical audio or
establish remote-server throughput. Metadata delay affects Item/User APIs,
not video bandwidth or packet loss.

## Media-open follow-up, 2026-10-06

The transport now hands the first validated media response to its read-ahead
producer, including the bytes already consumed for sniffing. It no longer
cancels that response and downloads the same prefix again. The producer keeps
its existing 32 MiB window, strong-validator checks and suffix recovery.
Foreground index reads wait for cancelled workers but add stream-release grace
only after a server refusal. A refusal after cancellation still triggers the
serial retry, including servers that release their stream slot late.

Run the Windows core through the production Dart proxy/cache with generated
media (fixtures from `tool/player_fixtures.py`):

```powershell
dart run tool/player_media_startup_bench.dart --media build/player-validation/media/tracks-long.mkv --latency-ms 250 --resume-ms 12000 --trials 3
```

This uses H.264/AAC multi-track MKV, a 12-second resume point, a fresh isolated
cache for every trial, 250 ms per HTTP response and 4 ms per 64 KiB chunk. It
measures a core **decoded** frame, not a displayed Flutter texture, physical
audio, TCP packet loss or the user's remote HEVC source. It records numeric
request offsets, source/media/core hashes and the Dart runtime. Initial trials
include cold-process/library effects; compare the groups, not a chosen minimum.

## Cache setup and adjacent metadata follow-up

Real-source numeric tracing found approximately 740 ms between transport setup
and registration, followed by two adjacent tail reads (1124-byte Tags and
12282-byte Cues), each costing approximately 280–290 ms. The current candidate
starts HTTP while disk cache initialization is pending and awaits storage before
publishing media. Validated small metadata reads within the final 64 KiB of a
large stable media file share one bounded suffix fetch. Downstream byte ranges,
ETag validation, stream-refusal fallback and the 32 MiB transfer bound remain
unchanged. Controlled tests cover HTTP reaching the origin before cache setup
completes, cancellation/late-cache disposal, and exact metadata response slices.
No real-server latency improvement is claimed before a fresh user playback.

Native probing/seek experiments showed no useful improvement and were removed;
the final candidate uses the original core source and retains Impeller.

### Local cache interference found during validation

Some `rillight_video_backend_test.dart` instances used the production temporary
cache root. Opening their default 2 GiB sessions invokes the existing shared
quota policy and can evict blocks from an active player's 8 GiB session. During
the reported missing-range incident, the player's last writer statistics still
reported 3,378,451,037 bytes and zero local evictions, while a fresh filesystem
inventory found 577 blocks totaling 2,145,685,361 bytes. Those old per-coordinator
statistics do not prove other processes preserved the files.

Every backend test that opens media now supplies an isolated temporary cache
root. Existing tests already verify that a smaller session on the *same* root
reclaims to the lower quota. This is a test-isolation fix, not a change to that
quota contract. The cyan seek-track fallback denotes byte coverage; after
initialization/index bytes are evicted it cannot promise media-time coverage.
The track colors were not altered to conceal missing data.

## Initial small-packet follow-up

The two real playback sessions after the previous rebuild opened the backend in
3077 ms and 2359 ms from controller start. The first still overlapped a pending
cache initialization with HTTP; established downloads reached approximately
20–26 MB/s. These are individual observations, not matched performance samples.

Two controlled issues were addressed:

- Known, stable session media requested in 64 KiB to sub-MiB ranges can now use
  the existing bounded read-ahead producer. Eight sequential 64 KiB reads use
  one continuous origin response after the initial representation probe. The
  first bytes are returned while that origin response remains incomplete.
  Tiny metadata and EOF probes retain their separate validated cache path;
  short initial responses are not mis-adopted as a larger producer response.
- Media HTTP responses disable Dart's small-write output buffer. A gated origin
  delivering only 1 KiB then waiting previously withheld the body from the native
  reader; it now reaches the reader before the gate is released. Both ordinary
  streaming and read-ahead have regression coverage. The fixture explicitly
  disables its own output buffer so this test measures the production proxy.
  Stream backpressure, disk-block coalescing, 32 MiB request bounds and serial
  refusal handling are retained.

A first-packet `flush()` experiment did not fix the buffering behavior and was
removed. Tests verify conditional completion and exact request counts rather
than impose a timing threshold on normal throughput. These synthetic tests do
not prove that every real-server startup delay has the same cause.

Native decoded-frame samples with the usual 64 KiB source chunks and 250 ms
request latency were 2199/1836/1840 ms before disabling the small-write output
buffer and 2183/1832/1800 ms afterwards. Medians of 1840 and 1832 ms show no
material improvement for this already-large-chunk fixture; do not market it as
a throughput/startup gain. The discriminating small-packet evidence is the gated
1 KiB test, which previously could not deliver the body while the origin waited.
Artifacts: `startup-small-range-native-bench.jsonl` and
`startup-small-packets-native-bench.jsonl`.

Final small-packet candidate validation: 1194 full-suite tests passed
(`startup-small-packets-final-tests.log`); static analysis and formatting passed.
The prior run's warm-handoff assertion expected the exact seek response extent;
it now checks that the requested interval is covered when read-ahead extends
beyond it. The final full rerun includes that corrected assertion.
Windows native smoke passed at
`build/player-validation/runs/20261006-101805-132/result.json`; the production
entrypoint was rebuilt afterwards (`startup-small-packets-native-smoke.log`).
The local app was restarted for real-source playback. Physical audio and
real-server cold-start latency changes are not established by these checks.
